## 1. Implementation steps

1. **System config (server-only)**  
   YAML ClassVar `ACTIVATE_AI_AGENTS` in `pvf_app_startup.yaml` / `PvfGlobalSettings` (same injection as Stripe). Env on `GlobalSettings`: `AI_SERVICE` (`opencode_go` | `opencode_zen`), `AI_API_KEY`, `AI_MODEL`, optional `AI_BASE_URL`. Enabled iff yaml on **and** key present. Document placeholders in `example.env`. Do **not** put key/model/service on `ClientSettings` or `customer.client_settings`. Context may expose only `ai_features_enabled: bool`. Default yaml **false** (gated release).

2. **LLM adapter**  
   New `src/utils/ai/` with a provider interface (chat + JSON). First adapter: OpenCode Go/Zen via `httpx`. Route by model to the documented family: Go `https://opencode.ai/zen/go/v1/{chat/completions|responses|messages}` vs Zen `https://opencode.ai/zen/v1/...`. v1 test on one Go **chat/completions** model (`glm-5.2`). Never return provider, model, or raw backend errors. Do not log the key.

3. **Factor suggest (sync, no persist)**  
   `POST /ws/custproject-content/factor-suggest` (customer_admin, same auth as factor-create). Input: title + description (body or saved project). Output: `[{title, description}]` only. UI: Factors tab button when title+description exist and `ai_features_enabled`. Prefill local list; user deletes/edits; existing `syncFactors()` persists. No auto-create DB rows.

4. **Port pair scheduler to Python**  
   Port `selectNextPair` / `acquisitionScore` / orientation / seeded noise from `client/utils/pairScheduler.ts` to `src/utils/pair_scheduler.py`. Golden tests: same seed + answers → same pair sequence as TS. Grouping already lives in `pick_next_sort_group`; add an optional pass cap so AI stops at `max_recommended_passes` (not `hard_max_passes = max+1`).

5. **AI participant identity**  
   Extend `VoteSource` with `ai`. One participant per project: `participant_key="ai:system"`, `display_name="AI baseline"`. Reuse `ProjectVoteGroupResult` (issue → pairings → complete). No new vote tables. Confirm enum storage is varchar (likely no Postgres ENUM alter).

6. **Background orchestration**  
   Implement the unused watcher-module dispatch in `powerchoice_watcher.py` (today `else: pass`). Admin trigger enqueues a job row; worker: ensure AI participant → `pick_next_sort_group` (capped) → Python `selectNextPair` → concise pairwise prompt (two item titles/descriptions + factor/overall context; constrained `winner|tie`) → `save`/`complete-group` until max groups or `session_complete`. Resume `in_progress`. Independent of human votes. Idempotent: skip if AI participant already complete. Factor-suggest stays on the request path.

7. **Results isolation**  
   Default `build_report` **excludes** `source=ai` so the human aggregate is unchanged. Emit sibling `ai_baseline` from AI groups only. Results UI: labeled “AI baseline”; never mixed into participant count or human coherence. Incomplete AI runs omitted until `is_complete`.

8. **Limits, failure, retry**  
   Env: timeout, retries, max concurrent AI projects, max pairs per project. Retry 429/5xx with backoff. After retries, record `skipped` and continue; if skip rate is high, leave participant incomplete (no baseline). Do not leak provider error bodies.

9. **Tests + gated default**  
   Unit: config absent from `/ws/core/context`; factor-suggest with mocked LLM; scheduler golden files; `build_report` human-only + `ai_baseline`. Integration: mocked watcher run persists `VoteSource.ai` groups. Keep `ACTIVATE_AI_AGENTS: false` until the gate is lifted.
