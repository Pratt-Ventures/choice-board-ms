## 1. Implementation steps

1. **System config (server-only)**  
   Add env: `AI_SERVICE` (`opencode_go` | `opencode_zen`), `AI_API_KEY`, `AI_MODEL`, optional `AI_BASE_URL`. Add startup ClassVar `ACTIVATE_AI_AGENTS` in `pvf_app_startup.yaml` / `PvfGlobalSettings` (same pattern as Stripe). Enabled iff yaml on **and** key present. Document in `example.env` with placeholders. Do **not** put key/model/service on `ClientSettings` or `customer.client_settings`. Context may expose only `ai_features_enabled: bool`. If any AI blob ever lands on customer records, add it to `CONTEXT_MASKED_FIELDS`.

2. **LLM adapter**  
   New `src/utils/ai/` with a provider interface (chat + JSON). First adapter: OpenCode Go/Zen via `httpx` (already used for SendGrid). Route by model to the documented endpoint family (`/zen/go/v1/chat/completions`, `/responses`, `/messages` vs `/zen/v1/...`). Prefer a Go **chat/completions** model for the first test (e.g. `glm-5.2` / `kimi-k2.6`) so v1 is one HTTP shape. Never return provider, model, or raw errors that name the backend.

3. **Factor suggest (sync, no persist)**  
   `POST /ws/custproject-content/factor-suggest` (admin, same auth as factor-create). Input: project title + description (from body or saved project). Output: `[{title, description}]` only. UI: Factors tab button when title+description exist and `ai_features_enabled`. Prefill the local factor list; user deletes/edits; existing `syncFactors()` persists. Do not auto-create DB rows.

4. **Port pair scheduler to Python**  
   Port `selectNextPair` / `acquisitionScore` / orientation / seeded noise from `pairScheduler.ts` to `src/utils/pair_scheduler.py`. Golden tests: same seed + answers → same pair sequence as the TS implementation. This is the parity-critical piece; grouping already lives in `pick_next_sort_group`.

5. **AI participant identity**  
   Extend `VoteSource` with `ai`. One participant per project: `participant_key="ai:system"`, `display_name="AI baseline"`. Reuse `ProjectVoteGroupResult` (issue → pairings → complete). No new vote tables. Cap the AI session at `max_recommended_passes` (not `hard_max_passes = max+1`).

6. **Background orchestration**  
   New watcher module (register on `WATCHER_PROCESS_MODULE_LIST`). Admin trigger enqueues a job (factor-suggest stays request-path). Worker: ensure AI participant → `pick_next_sort_group` → Python `selectNextPair` loop → concise pairwise prompt (two item titles/descriptions + factor/overall context; constrained `winner|tie`) → `save`/`complete-group` until max groups or session_complete. Resume `in_progress` groups. Independent of human votes. Idempotent: skip if an AI participant is already complete unless a re-run is explicitly requested.

7. **Results isolation**  
   Default `build_report` **excludes** `source=ai` so the human aggregate is unchanged. Emit a sibling `ai_baseline` slice from AI groups only. Results UI: labeled “AI baseline”, never mixed into participant count / coherence-among-humans. Incomplete AI runs are omitted from the baseline until `is_complete`.

8. **Limits, failure, retry**  
   Env caps: timeout, retries, max concurrent AI projects, max pairs per project. Retry 429/5xx with backoff. After retries, record `skipped` and continue so the group can finish; if skip rate is high, leave participant incomplete (no baseline). Do not leak provider error bodies to the client.

9. **Tests + gated default**  
   Unit: config not in `/ws/core/context`; factor-suggest with mocked LLM; scheduler golden files; `build_report` human-only + `ai_baseline`. Integration: mocked watcher run persists `VoteSource.ai` groups. Keep `ACTIVATE_AI_AGENTS: false` until the gate is lifted.

## 2. Clarifying questions

1. Enablement: system yaml+env only, or also a per-project “include AI baseline” toggle (boolean, no model/key)?
The provider, model, and key will be selected by the customer on a new settings page tombstone. The feature is disabled if that is not set up for the current customer. 
2. AI participant trigger: on-demand admin button, or automatic once title/description/options/factors are saved?
The main settings page for the project should have 'Invite AI participant?' with a yes/no toggle defaulting to no. These can flip anytime. Once started, it cannot be turned off. An extra button should say, 'Initiate now' and it will spin until complete, though the process should run to completion regardless.
3. “Maximum groups” = `max_recommended_passes` (recommended) or `hard_max_passes` (human extra pass)?
Use the max recommended groups only.
4. Re-run: block, replace AI groups, or keep first run only?
No option at this time, likely added later, but reset semantics would need to be identified.
5. Factor suggest: target count (e.g. 4–8)? overwrite unsaved local factors or merge? include polarity (stored, not in the editor)?
The AI should answer the same rough question pattern that a human would face, though it doesn't need the group interstitials, since each is a separate prompt with a standard prefix / base prompt. The server should duplicate the question selection process in the client for driving this conversation.
6. Pair answers: force a winner, or allow `tie` (and never `unsure`)?
All the same answers as a human for now.
7. First test model: OpenCode Go chat/completions (e.g. `glm-5.2`) vs a specific Zen model?
As mentioned above, the customer can now choose opencode go or openrouter, provide their key, and use any models they allow.
8. Results: overlay ranks next to humans, or a separate baseline block/tab?
On the results, we want to show the AI for comparison, but not as a proper voter. They should be able to see the relative ranking and factor importance for the AI, including the stability etc. A selection near the top, when AI was activated, saying 'Show AI only view,' 'Humans Only' and 'Show Combined' would work for now. In the 'Humans Only' view, a summary of the 'AI weighted ranking' and 'AI Factor importance' should be added at the bottom. In AI view, do the same for the 'Human Weighted ranking and 'Human Factor importance' (these titles are illustrative, pick good titles and make it look great).
9. Should the AI session wait until options/factors are frozen, or may it run while the editor is still changing?
This should be intended for when its frozen, though we don't really lock down the UI. I added a request for a start AI now button above, so that will gate it. Since we don't let them re-run it, users are encouraged to run only after locked down.

## 3. Options and trade-offs

**A. Config**  
- yaml flag + env secrets (Stripe pattern) vs env-only vs `customer.client_settings`.  
- **Recommend:** yaml `ACTIVATE_AI_AGENTS` + env credentials. Deployment gate without a UI that could leak secrets. `client_settings` is sent to the browser — reject it.

**B. Pair order**  
- Port scheduler to Python vs run Node vs leave pairing on the client.  
- **Recommend:** Python port + golden tests. Client pairing would expose the AI path to the browser; Node is a second runtime. Grouping is already server-side.

**C. Orchestration**  
- Sync HTTP vs watcher vs new queue.  
- **Recommend:** watcher for the AI participant (many sequential LLM calls; existing job plane). Factor-suggest can stay a short authenticated POST.

**D. Isolation**  
- `VoteSource.ai` vs new `GroupStatus` vs separate tables.  
- **Recommend:** `VoteSource.ai` + `ai:system` participant; filter in `build_report`. Meets “special status” without a second results pipeline. Optional later: `GroupStatus.ai_complete` if product wants per-group badges.

**E. LLM HTTP surface**  
- Full Go/Zen endpoint router vs OpenAI-compatible only.  
- **Recommend:** thin adapter with a model→endpoint map; v1 test on one Go chat/completions model. Zen/Go mix responses/messages/chat — implementing all three up front delays the feature.

**F. Factor persist**  
- Return suggestions only vs auto-`create_factor`.  
- **Recommend:** suggestions only. Matches “user can then delete and adjust” and reuses `syncFactors()`.

**G. Enablement UX (open in the brief)**  
- Hidden until yaml+key vs workspace boolean vs per-project.  
- **Recommend for v1:** system enablement; client sees only `ai_features_enabled`; two admin actions (Suggest factors, Run AI baseline). Per-project opt-out can be a later boolean column with no credentials.

Default until answered: (1) system-level only, (2) on-demand button, (3) `max_recommended_passes`, (4) no silent re-run, (5) 5–8 factors, merge into empty list / confirm replace if local factors exist, no polarity in UI, (6) allow `tie`, (7) OpenCode Go chat/completions model, (8) separate labeled baseline block, (9) require saved options + at least overall-or-factors before enqueue.
