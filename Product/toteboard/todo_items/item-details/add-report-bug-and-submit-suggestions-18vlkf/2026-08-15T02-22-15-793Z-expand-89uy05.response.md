**Expansion:** This feature adds user-communication dialogs for submitting bug reports and suggestions, available only to logged-in users via three new entries (Report a Bug, Submit a Suggestion, Check Submission Status) inserted in the account session pulldown immediately above the About item, backed by two new SQLModel tables (bug_reports, suggestions) that share a common baseline schema (integer id, customer_id, user_id, lifecycle dates/users/notes for acknowledge/response/resolution, creation/modification/soft-delete dates) and a mirrored "User Communication" service group. Submissions enforce a rolling-24-hour per-type cap (MAX_REPORTS_PER_DAY, default 10) with three tiers of response (successful n-of-x count, stored-with-warning when exceeded, discarded-with-log_entry-variable-capture when over by 1); a submit-status page shows recent suggestions first then bug reports (with 'No active suggestions found'/'No active bug reports found' states and circled-i hover notes), while a system-admin-only "System Admin" menu entry leads to paginated admin lists with an edit/delete overlay, plus soft-delete for users on their own pre-action submissions and admin-only modify/retrieve-all services. It should follow existing FastAPI/SQLModel/router patterns, alembic migrations, and the Vuetify client style guide, reusing shared common-code where possible (e.g., the AboutDialog pattern and ApplicationLogEvent's kw_details/details_json variable area).

- **Scope:** Backend — two SQLModel models + alembic migration, "User Communication" session service group with mirrored submit/retrieve-my/retrieve-admin/modify/soft-delete endpoints for each type, rate-limit logic with warning vs. discard semantics and n-of-x counts, customer-admin vs. user vs. system-admin authorization; Frontend — dialog forms (bug: summary*, what happened*, expected, steps, impact, optional attachment; suggestion: suggestion*, helps-with, area, importance, optional attachment), status page, and System Admin paginated pages with edit/delete overlay.
- **Key considerations:** Follow existing table/router conventions (src/db/models, src/api, src/api/request_types) and "standard naming" for dates; define system-admin concept consistently with current customer_admin handling; mirror every service per type rather than duplicating logic — prefer a common/generic baseline for both tables, services, and UI elements.
- **Key considerations:** Attachment handling (paste/upload screenshot/file) needs storage decision (existing branding_images-like path, base64, or binary endpoint) and content-size/type validation; rate-limit responses must include trailing-24h count and max (excluding buffer) so the client can render "n of x per day."
- **Key considerations:** Soft-delete rules (own submissions only before any admin action/update; admins any item), admin modify allows setting/clearing the three dates and editing the three note fields independently; admin list shows linked customer/user names, clipped summary, action dates or NA.
